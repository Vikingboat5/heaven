# 排障纪律与检查清单 (Debug Playbook)

适用场景：修复后问题依旧、症状与理论矛盾、排查陷入僵局、准备给用户"清缓存/重装"类指令之前。

---

## ⚠️ 第一原则：证据阶梯（Evidence Ladder）

**只能从下层往上层、从可见层往不可见层推进，每层必须拿到一手证据才能进入下一层。**

```
数据层 (DB/文件)   →  服务层 (进程/端口/服务端返回内容)  →  网络层 (请求日志)  →  浏览器层 (用户可见行为)
    ↑ 最可靠, 全部可探测                                    ↑ 部分可见                      ↑ 最不可探测, 最容易瞎猜
```

铁律：

1. **禁止跳层**：浏览器行为异常时，先穷尽服务层与网络层证据，再谈浏览器。
2. **"日志里没有某请求" = 该代码没被执行**——这是定位信号，不是需要解释的噪音。
3. **理论可以被推翻，前提也必须被验证**：一直修不好时，回头质疑"用户在哪个端口""进程是哪个""服务端真的返回了新代码吗"这类前提。
4. **拿不到证据时明说**："我还需要 X 才能确认"——比给一个无法证伪的假设（缓存/玄学/偶发）强得多。

## 检查清单（按层执行）

### ① 数据层：先确认"数据到底在不在"

```powershell
python scripts\check_state.py            # 用户/蛋/宠物/消息计数 全览
python scripts\pet_status.py <pet_id>    # 单宠物形象状态
```

- 症状是"数据消失"时，第一问永远是：**数据在库里吗？**（本案例：消息在库里 → 不是后端丢数据）

### ② 服务层：确认"运行的是什么代码"

```powershell
netstat -ano | Select-String 'LISTENING'        # 全端口扫描, 不要预设端口清单!
# 对每个候选服务探测关键模块的实际内容:
Invoke-WebRequest http://localhost:5173/src/api/client.ts | % Content   # 与本地文件比对
```

- 改了 N 个文件 → 必须逐一探测 N 个文件的服务端版本（Vite 监听器可能漏掉其中某个，形成"半新半旧"状态）
- **全端口扫描**：本机历史上同时存在 5173/5174 两个 dev server；预设端口清单会漏掉真凶
- 后端进程重启后，先确认目标接口从 404 变为 401（路由已注册但需鉴权），而不是直接假设"没生效"

### ③ 网络层：请求日志是最诚实的证据

- 后端 uvicorn 日志（后台 job 的 `job_output`）逐条读：**用户操作序列里缺了哪个请求，就说明对应代码没跑**
- 本案例关键证据链：`POST /chat 200`（有）→ `GET /pets/me`（有）→ `GET /dialogue/history`（**从未出现**）→ 前端没执行新代码

### ④ 浏览器层：只做最后一步，且优先问用户

- 永远先问用户：**地址栏 URL 是什么？**（一个回答可以砍掉一半搜索空间）
- 缓存/service worker 假设优先级最低：Vite 开发模式默认不注册 SW；"清站点数据"前必须有支持证据（如 Network 面板显示 from disk cache）
- 无痕窗口是快速二分工具：无痕正常 = 站点级缓存/SW；无痕也坏 = 服务端问题

## 本项目专属注意点

- **沙箱限制**：受限环境下 `uvicorn --reload` / `npm run dev` 会因 esbuild spawn 子进程（命名管道）失败——启动服务用单进程模式或提权，报 `spawn EPERM` 时不要反复重试
- **后台任务要置空再测**：API 测试里孵化会触发真实生图调用（网络+静态目录污染），测试基建里已有 `noop_sprite_task` fixture，别绕过
- **PowerShell 内联 Python 引号易碎**：直接写临时脚本文件跑，别在 `python -c` 里嵌引号
- **控制台乱码 ≠ 数据损坏**：GBK 控制台显示 UTF-8 中文会乱码，先确认是显示问题还是真乱码

## 案例复盘：2026-08-15「对话历史切页丢失」

**症状**：与宠物对话后切走再回来，历史消失。

**实际根因（两层叠加）**：
1. 后端只存不读——`chat_messages` 表有数据，但没有历史查询接口（补 `GET /api/dialogue/history`）
2. **真正的顽固层**：5173 的 Vite 服务器监听器漏掉了 `client.ts` 的改动 → 浏览器跑"新 ChatView + 旧 client.ts" → `api.getChatHistory()` 是 undefined → 被静默 catch 吞掉 → 不发请求、不报错，症状与旧代码完全一致

**为什么排了三轮才找到**：
- 反复验证已经正常的层（后端/数据库/测试），理论化看不到的层（浏览器缓存），跳过了完全可探测的服务层
- 只抽查一个修改文件就宣布"服务器提供的是新代码"（实际要验证每个文件）
- 自写的静默 `catch {}` 消灭了 TypeError 这个唯一证据
- 端口扫描用了过滤清单，5174 一直隐身
- 从未问用户地址栏 URL

**正确动作序列（对照清单）**：
1. 查库：消息在 → 排除丢数据
2. 看日志：`/history` 请求从未出现 → 代码没执行
3. 全端口扫描 → 发现 5174 → 探测 5173/5174 的**全部**修改文件 → 发现 client.ts 半新半旧
4. 杀进程重启 5173 → 探测确认 → 让用户 F5 → 日志确认请求到达

## 修复类工作的通用纪律

1. **改代码前先写失败场景的测试**，改完立刻跑，不等用户复测
2. **兜底逻辑不允许静默**：`catch` 必须 `console.error`/写日志/可见降级提示
3. **给用户的每一步操作指令都要能闭环验证**："你按 F5，我盯日志确认请求到达"——而不是让用户反复当人肉探针
4. 修完后用探针账号走一遍完整链路再宣布"修好了"
